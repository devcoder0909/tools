## The Computer Science of 100KB Compression: DCT & Quantization Math

Compressing an image from 5MB down to 100KB represents a **98% data reduction**. Understanding how lossy compression achieves this without ruining visual realism explains why ZixTool outperforms traditional cloud converters:

### 1. RGB to YCbCr Matrix Conversion & Chrominance Subsampling
Natural photographs record light in RGB (Red, Green, Blue) space. The human retina contains roughly 120 million luminance-sensitive rod cells and only 6 million color-sensitive cone cells. ZixTool converts RGB to **YCbCr space**:
- **$Y$ (Luminance):** Grayscale brightness, capturing sharp geometric edges and fine facial lines.
- **$Cb$ and $Cr$ (Chroma):** Blue-difference and red-difference color nuances.

By applying **4:2:0 chrominance subsampling**, the horizontal and vertical resolution of color channels is halved. This discards 50% of the raw color matrix before quantization begins, with zero perceptible loss in photographic sharpness.

### 2. The $8 \times 8$ Discrete Cosine Transform (DCT)
The image is divided into regular blocks of $8 \times 8$ pixels. The forward Discrete Cosine Transform maps spatial pixel intensities into 64 frequency coefficients:

$$F(u,v) = \frac{1}{4} C(u) C(v) \sum_{x=0}^{7} \sum_{y=0}^{7} f(x,y) \cos\left[\frac{(2x+1)u\pi}{16}\right] \cos\left[\frac{(2y+1)v\pi}{16}\right]$$

Low-frequency coefficients (representing general color tones) cluster in the top-left, while high-frequency noise and microscopic textures congregate in the bottom-right.

### 3. Psycho-Visual Quantization & Huffman Coding
Each frequency coefficient is divided by a value from a standardized psycho-visual quantization table:

$$F_Q(u,v) = \text{round}\left( \frac{F(u,v)}{Q(u,v)} \right)$$

Our 100KB target engine sets $Q(u,v)$ to round high-frequency noise down to zeros while protecting the low- and mid-frequency visual bands. A zigzag scan groups these zeros, which are then compressed losslessly using Run-Length Encoding (RLE) and Huffman entropy coding.

## Binary (102,400 Bytes) vs Decimal (100,000 Bytes) Ceilings

A major reason candidate uploads fail on government portals is the subtle difference between binary and decimal byte accounting:
- **Binary Kilobyte (KiB):** $100\text{ KiB} = 100 \times 1,024 = \mathbf{102,400\text{ bytes}}$. Windows File Explorer and Linux report file sizes using this binary standard.
- **Decimal Kilobyte (KB):** $100\text{ KB} = 100 \times 1,000 = \mathbf{100,000\text{ bytes}}$. Some strict web validators use decimal division ($100,000$ bytes). If a file measures $101,200$ bytes, Windows displays "99 KB", but the upload portal rejects it as "101.2 KB".

ZixTool calibrates its 100KB ceiling conservatively to ensure your compressed file remains strictly beneath **$98,000\text{ to } 100,000\text{ bytes}$**, guaranteeing 100% upload acceptance across both binary and decimal server validators.
