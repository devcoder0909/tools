## The Computer Science of CSV Parsing: RFC 4180 Standards & Edge Cases

While comma-separated values appear simple on the surface, naive string splitting (`line.split(',')`) fails across numerous real-world enterprise spreadsheet scenarios. ZixTool implements a state-machine lexical tokenizer adhering to the official **IETF RFC 4180 standard**:

### 1. Escaping Commas within Quoted Fields
When a data cell contains an intentional comma—such as an address (`"100 Main St, Suite 400"`) or an author's name (`"Smith, John"`)—RFC 4180 mandates enclosing the cell in double quotes (`"`). Naive parsers split these entries into two fragmented columns, corrupting the entire database row.

### 2. Double-Quote Escaping (Quote Doubling)
If a text field contains literal quotation marks, the character is escaped within quotes by preceding it with another double quote:

$$\text{Raw CSV Input: } \text{"The CEO stated, ""Record quarterly growth was achieved."""}$$

$$\text{Parsed JSON: } \text{"The CEO stated, \"Record quarterly growth was achieved.\""}$$

### 3. Multi-Line Cell Records
In customer feedback forms, medical notes, or bug reports, a single table cell frequently spans multiple lines containing newline breaks (`\r\n` or `\n`). An RFC 4180-compliant parser tracks quotation state across line breaks, ensuring that multi-line text remains bundled inside a single JSON string property rather than fragmenting into multiple erroneous rows.

### 4. International Delimiters (The European Semicolon Standard)
In many European countries (such as Germany, France, and Italy), the comma (`,`) serves as the decimal separator (e.g., `12,50 €`). Consequently, Microsoft Excel in these locales exports CSV files using **semicolons (`;`)** as column delimiters. ZixTool features intelligent delimiter autodetection, automatically identifying commas, semicolons, tabs (`\t`), and pipes (`|`).

## Data Type Inference: Strings vs Native JSON Primitives

In raw CSV files, all data is stored without explicit type metadata; every cell is technically a sequence of text characters. When converting to JSON, raw string representation often degrades API performance. ZixTool features intelligent automatic type coercion:

- **Integer & Float Numbers:** Strings like `"42"` or `"199.95"` are converted to native JSON numeric primitives (`42`, `199.95`) rather than stored as text strings (`"42"`).
- **Boolean Values:** Case-insensitive strings like `"true"`, `"false"`, `"TRUE"`, or `"FALSE"` are parsed directly into native JavaScript booleans (`true`, `false`).
- **Null and Empty States:** Unpopulated cells (`,,`) can be configured to map to `null`, an empty string `""`, or omitted from the object payload entirely.
- **Scientific Notation:** Numbers formatted like `"1.5e4"` are evaluated to their numerical value ($15,000$).

## Structured Output Options: Array of Objects vs Array of Arrays

Depending on your target API or software architecture, ZixTool supports flexible JSON serialization modes:

### 1. Array of Key-Value Objects (Standard Mode)
The first row of the CSV is interpreted as dictionary keys for each subsequent object:
```json
[
  { "id": 1, "product": "Mechanical Keyboard", "price": 129.99, "inStock": true },
  { "id": 2, "product": "Wireless Mouse", "price": 59.50, "inStock": false }
]
```
*Best Used For:* REST API payloads, frontend component props, and MongoDB collection imports.

### 2. Array of Arrays (Compact 2D Matrix)
Omits repeated property keys, storing data as a compact array of rows:
```json
[
  ["id", "product", "price", "inStock"],
  [1, "Mechanical Keyboard", 129.99, true],
  [2, "Wireless Mouse", 59.50, false]
]
```
*Best Used For:* High-volume data transmission where network bandwidth and payload size must be minimized.
