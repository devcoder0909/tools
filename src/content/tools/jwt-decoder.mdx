## The Computer Science of JSON Web Tokens: RFC 7519 Architecture

Standardized under **IETF RFC 7519**, a JSON Web Token is a compact, URL-safe means of representing claims to be transferred between two parties. A standard JWS (JSON Web Signature) token comprises three distinct segments joined by periods (`.`):

$$\text{JWT Token} = \text{Base64URL}(\text{Header}) \, . \, \text{Base64URL}(\text{Payload}) \, . \, \text{Base64URL}(\text{Signature})$$

### 1. Base64URL Encoding vs Standard Base64
Many developers mistakenly assume JWT payloads are encrypted. In reality, JWT tokens are merely **encoded** using **Base64URL (RFC 4648 §5)**:
- Standard Base64 uses the characters `+` and `/`, alongside trailing `=` padding characters. In HTTP URLs and cookies, these characters carry syntactic delimiter meanings and require percent-encoding (`%2B`, `%2F`, `%3D`).
- Base64URL replaces `+` with `-` (minus), replaces `/` with `_` (underscore), and strips all trailing `=` padding characters. This makes the resulting string completely safe to pass in HTTP request headers (`Authorization: Bearer <token>`), URL query parameters, and cookie payloads without escaping.
- **Critical Security Principle:** Any party who intercepts or views a JWT can immediately read the header and payload claims. Never store unencrypted passwords, API secret keys, or sensitive customer PII inside a standard JWT payload.

## Cryptographic Signing Algorithms: HMAC vs RSA vs ECDSA

The token header specifies the cryptographic algorithm (`alg`) used by the authentication server to generate the digital signature (RFC 7515):

### 1. Symmetric Signatures (HS256, HS384, HS512)
Utilizes a single **shared symmetric secret key** across both the issuing authentication server and the verifying API service. The server computes a Hash-based Message Authentication Code:

$$\text{Signature} = \text{HMAC-SHA256}(\text{EncodedHeader} + "." + \text{EncodedPayload}, \text{SharedSecret})$$

*Limitation:* Every backend microservice that verifies the token must possess the identical secret key. If any microservice is compromised, an attacker can forge administrative tokens for the entire enterprise.

### 2. Asymmetric Public-Key Signatures (RS256, RS384, RS512)
Utilizes an **RSA private/public key pair** (typically 2048-bit or 4096-bit). The central identity provider (such as Auth0, Okta, Keycloak, or AWS Cognito) signs the token with its private key. Distributed resource servers verify the signature using the publicly exposed JSON Web Key Set (JWKS) available at `/.well-known/jwks.json`, preventing private key exposure.

### 3. Elliptic Curve Signatures (ES256, ES384, ES512)
Uses Elliptic Curve Digital Signature Algorithm (ECDSA) with NIST prime curves (such as P-256 for ES256). Provides cryptographic security equivalent to 3072-bit RSA with substantially shorter key lengths and lower CPU computational overhead, making it ideal for mobile devices and high-throughput microservices.

## Standard Registered JWT Claims Reference Table

The table below outlines official claims defined in RFC 7519 Section 4.1 alongside standard industry usage:

| Claim Key | Standard Claim Name | Data Type | RFC Definition & Purpose | Verification Rule |
| :--- | :--- | :--- | :--- | :--- |
| **`iss`** | Issuer | String | Identifies the principal identity authority that issued the token | Must match the expected auth domain |
| **`sub`** | Subject | String | Unique identifier representing the authenticated user or service | Used as database primary key / UUID |
| **`aud`** | Audience | String / Array | Identifies the intended recipients or backend APIs for the token | Server rejects token if audience does not match |
| **`exp`** | Expiration Time | Unix Timestamp | Identifies the exact second the token ceases to be valid | Server rejects token if $\text{CurrentTime} \ge \text{exp}$ |
| **`nbf`** | Not Before | Unix Timestamp | Identifies the time before which the token must not be accepted | Server rejects if current time is prior to timestamp |
| **`iat`** | Issued At | Unix Timestamp | Records the creation second of the authentication token | Used to evaluate token age and max session length |
| **`jti`** | JWT ID | String (UUID) | Unique identifier for the token | Used in Redis token blacklists to prevent replay attacks |

## Critical JWT Security Vulnerabilities in Web Applications

Improper implementation of JSON Web Token verification libraries has led to major real-world corporate data breaches:

### 1. The `alg: "none"` Authentication Bypass
Early implementations of several open-source JWT libraries supported an unauthenticated algorithm variant specified in the RFC as `none`. Attackers forged administrative payloads, modified the token header to `{"alg": "none"}`, stripped the signature segment, and submitted the token. Vulnerable backends accepted the unverified token, granting full administrative privileges. Modern servers must explicitly whitelist allowed algorithms (e.g., only `RS256`).

### 2. The Algorithm Confusion Attack (HMAC vs RSA)
In an algorithm confusion attack, an attacker intercepts a token signed with asymmetric RS256. The attacker takes the server's public key (which is publicly accessible via JWKS), alters the token header to `{"alg": "HS256"}`, and signs the forged payload using the public key as the symmetric HMAC secret. If the backend verification library fails to verify the algorithm type, it verifies the signature using its public key as an HMAC secret, allowing forged authentication.

### 3. Client-Side Storage: `localStorage` vs `HttpOnly` Cookies
Storing sensitive JWT authentication tokens in browser `localStorage` or `sessionStorage` exposes the session to **Cross-Site Scripting (XSS)** attacks. Any rogue third-party script, malicious npm package dependency, or injected markup can read `localStorage.getItem('token')` and exfiltrate user sessions. Production applications should store authentication tokens in secure, `HttpOnly`, `SameSite=Strict` browser cookies inaccessible to JavaScript.
